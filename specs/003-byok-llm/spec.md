# Feature Specification: Bring-Your-Own-Key LLM

**Feature Branch**: `003-byok-llm`

**Created**: 2026-11-15

**Status**: Implemented

**Input**: User description: "Allow a visitor to supply their own LLM API
key so the platform can produce real LLM answers without the operator paying
for tokens."

## Why

The platform runs at zero cost with a deterministic (heuristic) answerer. A
visitor therefore never sees the quality of a real LLM answer, and the operator
cannot afford to pay for every visitor. Bring-Your-Own-Key (BYOK) closes that
gap: the visitor pays for exactly their own usage, and no secret ever has to be
stored.

This is also a security question interviewers ask: *where does a third-party
credential live, and what happens to it?* The answer here is deliberately
narrow: it lives in the browser tab, travels over the existing HTTPS proxy in a
single header, is used for the duration of one request, and is never written to
the database, the vector store, the traces, or the logs.

## User Scenarios & Testing

### Primary user story

As a visitor, I paste my OpenAI / Groq / OpenRouter key in the UI, verify it,
and the next answer is generated by my model instead of the extractive
fallback. When I close the tab the key is gone.

### Acceptance scenarios

1. **Given** a valid key, **When** I send a chat question, **Then** the
   provider receives `Authorization: Bearer <my key>`, the answer comes from
   the model, and the response/trace record never contains the key.
2. **Given** no key, **When** a non-admin chats, **Then** the heuristic pipeline
   answers exactly as today (no external call, no error) unless the deployment has a
   server key and BYOK is enabled, in which case the API answers `402`.
3. **Given** a key for a provider outside the allow-list, **When** I try to use
   it, **Then** the API answers `400` with a message naming the allowed
   providers, before any outbound request is made.
4. **Given** an invalid key, **When** I press "verify", **Then** I see the
   provider's status (401/403) in plain language, without the key being echoed.
5. **Given** the operator sets `LLM_API_KEY`, **When** a visitor supplies their
   own key, **Then** the visitor's key wins for that request only. The next request
   without the header uses the server key only when the caller is an admin;
   otherwise it returns `402` (or uses heuristics when BYOK is off).
6. **Given** an operator sets `LLM_BYOK_ENABLED=false`, **Then** any request
   carrying a user key is rejected with `403`, the UI hides the feature, and
   non-admin chat answers with the deterministic heuristics.

### Edge cases

- Key with whitespace, control characters, or length > 200 → `400` before any
  network call.
- Empty header (`X-LLM-API-Key: `) is treated as "no key", not as an error.
- Provider timeout / unreachable → the pipeline degrades to the heuristic
  answer; the user is not shown a stack trace.
- Provider `429` during verification → `429` with a "quota" message.
- Streaming chat: the key exists only inside the request that created the
  stream; a later request cannot reuse it.
- Multi-worker deployment: the override is request-scoped, so nothing leaks
  across workers.

## Requirements

### Functional

- **FR-001**: The API MUST accept `X-LLM-API-Key`, optionally accompanied by
  `X-LLM-Model` and `X-LLM-Base-URL`, on `POST /api/v1/chat` and
  `POST /api/v1/llm/verify`.
- **FR-002**: A supplied key MUST override the server key **only** for the
  request that carried it.
- **FR-003**: The key MUST NOT be persisted (no SQLite row, no file, no vector
  payload), logged, included in traces, or echoed in any response.
- **FR-004**: `X-LLM-Base-URL` MUST be checked against an allow-list
  (`LLM_ALLOWED_BASE_URLS`); a value outside it is rejected without an outbound
  request.
- **FR-005**: `POST /api/v1/llm/verify` MUST check the credential with the
  provider and return `{ok, provider, model, models}` or a safe error.
- **FR-006**: With no user key the behaviour MUST match today's pipeline: the
  heuristic answerer when `LLM_API_KEY` is empty, the server key when the caller
  is an admin, and `402` (or heuristics when BYOK is off) for everyone else.
- **FR-007**: `LLM_BYOK_ENABLED=false` MUST disable the feature and make the
  UI hide it (`GET /health` reports `byok: false`).
- **FR-008**: The server key (`LLM_API_KEY`) MUST answer for administrators only.
  A non-admin chat without a user key returns `402` with
  `X-LLM-Key-Required: 1` when BYOK is enabled, and never spends the server key.
  `GET /health` reports `server_key_admin_only: true`.
- **FR-008**: BYOK chat requests MUST obey the existing per-IP `chat` rate
  limit; verification gets its own bucket.
- **FR-009**: `LLM_MAX_TOKENS` MUST cap completion size for both server and
  user keys, and the BYOK timeout MUST be at most 30 s.

### Non-functional

- No new runtime dependency: `httpx` is already used for the LLM call.
- No new paid service and no change to the zero-cost default.
- The browser stores the key in `sessionStorage` only; `localStorage` is
  forbidden because it survives tab close and is exposed to XSS for longer.
- The Next.js proxy forwards only the three documented headers and nothing
  more.

## Success Criteria

- **SC-001**: A test proves the provider receives the user's key and not the
  server's.
- **SC-002**: A test proves the key is absent from `caplog` output and from
  every `traces.data_json` row after a BYOK chat.
- **SC-003**: A test proves a disallowed base URL is rejected before
  `httpx.post` is reached.
- **SC-004**: `pytest` and `tsc --noEmit` stay green, and the evaluation
  harness (which never sends a key) keeps its numbers.
- **SC-005**: Closing the tab removes the key (manual check documented in
  `quickstart.md`).

## Assumptions

- Visitors use a provider that exposes the OpenAI-compatible
  `/chat/completions` and `/models` routes (OpenAI, Groq, OpenRouter).
- The visitor understands that a key pasted into a web app transits that app's
  server; the UI states this once, plainly.
- Rate limiting is still per IP; a user key does not bypass it.

## Out of scope

- OAuth or provider-side device flows.
- Encrypted at-rest storage of user keys (deliberately none).
- Arbitrary custom base URLs (blocked to avoid SSRF and key exfiltration).
